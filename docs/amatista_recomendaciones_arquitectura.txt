AMATISTA PWA
RECOMENDACIONES DE ARQUITECTURA Y ORGANIZACIÓN DEL PROYECTO
===========================================================

1. VISIÓN GENERAL
-----------------

Amatista está bien encaminado como una plataforma educativa orientada al aprendizaje práctico de creación 3D para web/XR.

La idea central puede resumirse así:

Blender
  ↓
Exportación de modelos GLB
  ↓
A-Frame / WebXR
  ↓
Experiencia educativa interactiva
  ↓
Funcionamiento offline mediante PWA
  ↓
Sincronización con backend
  ↓
Tutor IA como capa adicional

La organización actual del repositorio tiene sentido y no necesita una reestructuración grande en este momento.

Estructura actual:

amatista/
├── frontend/
├── backend/
├── ai_tutor/
└── docs/

Esta separación es adecuada porque cada carpeta representa una responsabilidad distinta del sistema.


2. PRINCIPIO ARQUITECTÓNICO PRINCIPAL
-------------------------------------

La recomendación más importante es que Amatista siga un enfoque:

LOCAL PRIMERO, SERVICIOS EXTERNOS DESPUÉS.

La PWA debe poder realizar las funciones educativas principales aunque no tenga conexión a Internet.

Arquitectura recomendada:

Usuario
  ↓
PWA
  ↓
IndexedDB
  ↓
Contenido educativo disponible
  ↓
Progreso almacenado localmente

Cuando existe conexión:
  ↓
Backend
  ↓
Sincronización del progreso

Cuando el Tutor IA está disponible:
  ↓
Ollama
  ↓
Asistencia contextual

El funcionamiento de la plataforma no debería depender completamente del backend ni del Tutor IA.

4. RESPONSABILIDAD DE CADA MÓDULO
---------------------------------

4.1 FRONTEND

Debe ser el núcleo principal de Amatista.

Responsabilidades:

- Interfaz del estudiante.
- Dashboard.
- Ruta de aprendizaje.
- Lecciones.
- Visor 3D con A-Frame.
- Experiencias WebXR.
- Estado Online / Offline.
- Descarga de contenido.
- IndexedDB.
- Service Worker.
- Progreso local.
- Sincronización con backend.
- Comunicación con el Tutor IA.

La plataforma educativa debería seguir funcionando aunque el backend no esté disponible.


4.2 BACKEND

Debe actuar principalmente como servicio de persistencia y sincronización.

Responsabilidades:

- API.
- Usuarios.
- Progreso del estudiante.
- Sincronización de progreso.
- Metadatos de cursos.
- Registro de dispositivos o sesiones.
- Persistencia en Oracle.
- Validaciones del servidor.

El backend no debería convertirse en un requisito para visualizar contenido que ya está descargado localmente.


4.3 AI_TUTOR

Debe ser una capa adicional de asistencia.

Responsabilidades:

- Comunicación con Ollama.
- Prompts del sistema.
- Contexto educativo.
- Contexto de la lección actual.
- Explicaciones.
- Ayuda técnica.
- Resolución de dudas.
- Orientación paso a paso.

La plataforma debería seguir funcionando aunque Ollama no esté disponible.


4.4 DOCS

Debe contener la documentación técnica y las decisiones del proyecto.

Recomendaciones:

docs/
├── arquitectura.md
├── convenciones_commits.md
├── offline-first.md
├── api.md
├── base_datos.md
├── tutor_ia.md
├── decisiones/
└── diagramas/

La carpeta docs puede convertirse en la referencia técnica principal del proyecto.

8. FLUJO PRINCIPAL QUE DEBERÍA GUIAR EL DESARROLLO
---------------------------------------------------

El objetivo principal debería ser conseguir primero este recorrido completo:

1. El estudiante abre Amatista.
2. Visualiza su ruta de aprendizaje.
3. Descarga una lección.
4. El contenido se guarda localmente.
5. El estudiante pierde la conexión.
6. La lección sigue disponible.
7. Puede visualizar el modelo 3D.
8. Puede realizar la actividad.
9. El progreso se guarda en IndexedDB.
10. Recupera la conexión.
11. La aplicación detecta conectividad.
12. El progreso se sincroniza con el backend.
13. Opcionalmente el estudiante consulta al Tutor IA.

Cuando este flujo funcione de extremo a extremo, Amatista tendrá un MVP técnicamente sólido.

10. RECOMENDACIONES SOBRE LA ORGANIZACIÓN ACTUAL
------------------------------------------------

La estructura general actual debería mantenerse.

No es recomendable reorganizar continuamente el repositorio.

La arquitectura actual ya proporciona suficiente separación entre responsabilidades.

En este momento el mayor beneficio vendrá de implementar funcionalidades reales, no de crear más carpetas.

Regla recomendada:

NO CREAR UNA CAPA NUEVA HASTA QUE EXISTA UNA NECESIDAD REAL.

Ejemplo:

No crear veinte componentes antes de tener varias pantallas.

No crear múltiples servicios de backend antes de tener endpoints reales.

No crear una arquitectura compleja del Tutor IA antes de tener una comunicación básica con Ollama.

13. IDENTIDAD TÉCNICA DEL PROYECTO
----------------------------------

Amatista no debería presentarse simplemente como:

"una plataforma de cursos".

Una definición más clara sería:

"Plataforma educativa offline-first para aprendizaje práctico de creación 3D orientada a WebXR, integrando Blender, modelos GLB, A-Frame y asistencia mediante IA local."

Esta definición refleja mejor la diferenciación técnica del proyecto.


14. RIESGOS PRINCIPALES
-----------------------

El principal riesgo no es la arquitectura.

El principal riesgo es intentar desarrollar simultáneamente demasiadas tecnologías:

- React.
- PWA.
- IndexedDB.
- Service Worker.
- A-Frame.
- WebXR.
- Python.
- Oracle.
- Cloudflare.
- Ollama.
- Túneles.
- Sincronización.

La solución es desarrollar verticalmente.

En lugar de construir cada sistema completo por separado:

Frontend completo
Backend completo
IA completa
Base de datos completa

es preferible construir una funcionalidad completa de principio a fin.

Ejemplo:

Lección
  ↓
descarga
  ↓
almacenamiento local
  ↓
visualización 3D
  ↓
actividad
  ↓
progreso
  ↓
sincronización

Después se amplía el sistema.


15. RECOMENDACIÓN FINAL
-----------------------

La arquitectura general de Amatista está bien planteada.

La organización:

frontend/
backend/
ai_tutor/
docs/

es adecuada y debería mantenerse.

El proyecto debería avanzar bajo tres principios:

1. OFFLINE-FIRST
La funcionalidad educativa principal debe funcionar sin Internet.

2. FRONTEND COMO NÚCLEO
La experiencia del estudiante debe ser el centro de la arquitectura.

3. SERVICIOS COMO CAPAS ADICIONALES
Backend e IA deben mejorar la experiencia, pero no impedir que la plataforma funcione si no están disponibles.

La siguiente etapa de Amatista no debería centrarse en reorganizar el repositorio.

Debería centrarse en conseguir que un estudiante pueda:

abrir Amatista
→ descargar una lección
→ quedarse sin conexión
→ estudiar
→ visualizar el contenido 3D
→ completar una actividad
→ guardar su progreso
→ recuperar conexión
→ sincronizar su progreso

Cuando ese recorrido funcione correctamente, la arquitectura dejará de ser solamente una buena planificación y se convertirá en una base sólida para hacer crecer todo el proyecto.
